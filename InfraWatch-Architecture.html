Key design choices

  • Event-driven core: every incident/change/runbook action is an event on the bus → audit trail, notifications, search indexing and AI training all consume the same stream.
  • Evidence snapshots: when Prod Support attaches graphs/logs, a frozen copy (query + data) is saved in object storage, so training data survives retention limits of the live TSDB.
  • RBAC by group: assignment groups drive visibility, DL mail routing and who may update the status bar.
  • OpenTelemetry-first: vendor-neutral collection; the same signals feed dashboards, alerting and the AI.

Notification logic

  • To: assignment-group distribution list (from Team Service).
  • CC: current on-call(s) resolved from the roster at send time (devs maintain it in-app).
  • Triggers: created, reassigned, severity change, status change, runbook due, closed.
  • Mail threading: one thread per incident (Message-ID / In-Reply-To) so replies can be ingested into the timeline later.

AI & data pipeline — predicting root cause

Runbooks are the ground truth. Everything else (telemetry, tickets, changes, chat) gives the model context. Start with retrieval over past incidents; add trained models once enough labelled incidents exist.

Data / inference flow Feedback loop (labels → re-index / retrain)

Additional data sources worth capturing (beyond observability + tickets)

Deploys, releases & config changes MUST

CI/CD events, Git commits, feature-flag flips, infra-as-code applies. Most incidents follow a change.

Service topology / CMDB MUST

Dependency graph and ownership so the model knows what an upstream failure affects.

War-room chat & shift handovers MUST

Teams/Slack incident channels and the Prod Support handover log — rich reasoning that never reaches the ticket.

Alert history & noise SHOULD

Which alerts fired, in what order, which were ignored — great for correlation.

SLO / error-budget burn SHOULD

Customer-facing health signal; helps rank incidents by real impact.

Kubernetes & cloud events SHOULD

Pod restarts, OOMKills, node drains, cloud provider health events and quota limits.

DB slow queries & locks SHOULD

Query plans, wait events, connection pool saturation — frequent root causes.

Synthetic checks / RUM SHOULD

What users actually experience, independent of internal metrics.

Third-party status & certificates LATER

Vendor status pages, certificate/domain expiry, DNS and network flow data.

Security events LATER

WAF, IAM and audit events — separates attacks / permission changes from faults.

Calendar & business context LATER

Release freezes, month-end, campaigns, planned maintenance — explains traffic patterns.

Historical backfill MUST

Import old tickets/postmortems (e.g. from ServiceNow/Jira, wikis) to bootstrap the knowledge base from day one.

Keeping the AI in pace with production

  • Production Pulse: a short daily entry by Prod Support/SRE — known issues, risky releases, freeze windows, workarounds. Fed straight into the AI context.
  • Shift handover as data: handover notes are structured records, not free mail.
  • Change calendar feed: upcoming & recent changes injected into every suggestion.
  • Feedback buttons: on every AI suggestion (“correct / partly / wrong”); the runbook's confirmed root cause is compared with the prediction automatically.
  • Weekly review: SRE + Prod Support review prediction accuracy, stale runbooks and taxonomy gaps.
  • Staleness flags: runbooks not validated after related architecture/changes are flagged for review.
  • Drift monitoring: track accuracy over time and retrain/re-index on a schedule or after major platform changes.

Suggested AI approach (honest expectations)

  • Stage 1 – Retrieval (RAG): “similar past incidents + their runbooks + current telemetry” summarised by an LLM. Works with tens of incidents.
  • Stage 2 – Correlation: anomaly detection and alert/change correlation around incident time → ranked evidence.
  • Stage 3 – Supervised RCA classifier: predict root-cause category once there are several hundred well-labelled incidents per major category.
  • Always show evidence (graphs, log lines, change IDs) with each prediction; keep a human in the loop.
  • Data hygiene: a fixed root-cause taxonomy and mandatory runbook fields matter more than model choice.
  • Privacy: scrub PII/secrets before indexing; keep models and vector store inside your boundary if required.

Suggested phasing

Phase 1 · Foundation

SSO + RBAC, teams & on-call roster, incident CRUD, group mail with on-call CC, status bar, timeline.

Phase 2 · Observability

OTel collection, dashboards/alerts, one-click “attach evidence snapshot” to incidents.

Phase 3 · ITSM completeness

Change & Request workflows with approvals, SLA engine, runbook template and close-gate, Problem records for repeat incidents.

Phase 4 · Knowledge & AI

Backfill history, vector index, similar-incident suggestions → correlation → trained RCA model with feedback loop.

Decisions confirmed

  • Standalone: InfraWatch fully replaces ServiceNow — no sync/integration. Old tickets can optionally be imported once (CSV) for AI bootstrapping.
  • Scope: side project for now → keep it lean; the architecture on tab 2 is the target shape, not the day-one deployment.
  • AI: external LLM API is acceptable for now (scrub PII/secrets before sending); keep the LLM behind one service so it can be swapped for a self-hosted model later.
  • Closing: the caller or any member of the caller's assignment group can close, and only after the runbook is approved.

Lean “side-project” stack (suggested)

Single deployable app

One modular backend (monolith with clear modules for Incident, Change/Request, Teams/On-call, Runbook, Notifications) instead of 8 microservices.

PostgreSQL — system of record

Tickets, teams, on-call, runbooks, audit. Free: Neon / Supabase free tier, or the Docker container.

Kafka — event backbone

Topics incident.*, change.*, runbook.*, alert.*, feedback.*. Free: self-hosted single-broker KRaft in Docker (or a Confluent Cloud / Redpanda trial if you want managed).

OpenSearch — search & logs

Full-text over tickets/runbooks, change events, optionally logs. Free: single-node in Docker (small heap), or the AWS OpenSearch 12-month free tier.

Vector DB — similar-incident search

Embeddings of runbooks/tickets/chat. Free: Qdrant Cloud free cluster (or Qdrant in Docker). OpenSearch k-NN is an alternative that avoids one extra service.

Prometheus + Grafana-style data

Prometheus (or VictoriaMetrics) + Loki via OpenTelemetry Collector; the app embeds/queries them and stores evidence snapshots in local disk or S3-compatible storage.

Docker Compose

Everything runs locally or on one VM; move to Kubernetes only if it grows.

Email via SMTP

Any SMTP relay for the group DL + on-call CC to start; inbound reply-parsing can come later.
